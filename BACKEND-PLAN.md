# BACKEND-PLAN.md — план бэкенда «Нейро.Студия» (с заделом на переиспользование)

Составлено на основе [research.md](research.md), [brief.md](brief.md) и уже реализованного `tg-app/`.

**Уточнённая задача** (после первого черновика плана оказалось, что я неверно понял сценарий с «мастерами» — исправляю):

- Прямо сейчас бэкенд нужен для **одного вашего бизнеса** — «Нейро.Студия», один бот, ваши услуги.
- Но идею продавать похожие боты другим клиентам в будущем вы не хотите игнорировать — поэтому структура данных с самого начала рассчитана на несколько независимых «бизнесов», а не жёстко вшита в один. Когда появится клиент, которому вы продаёте такого бота, — это будет **новая строка в базе**, а не копирование кода.
- Никакого самостоятельного онбординга посторонних людей («мастеров», которые сами себе всё настраивают») — **не строим**. Новый бизнес в системе заводите только вы, вручную, когда реально продаёте кому-то такого бота.

## 1. Модель данных

### `businesses` — один бизнес (сейчас единственная запись — «Нейро.Студия», ваша)
| Поле | Тип | Комментарий |
|---|---|---|
| id | uuid | PK |
| owner_telegram_id | bigint | ваш Telegram ID (или клиента, если это его бизнес) |
| bot_token | text, **encrypted** | токен из @BotFather (у вас уже есть — см. `.env`) |
| bot_username | text | |
| brand_name | text | «Нейро.Студия» |
| logo_emoji / logo_url | text | |
| accent_color | text | hex, по умолчанию `#2AABEE` |
| google_refresh_token | text, **encrypted**, nullable | если подключён календарь |
| google_calendar_id | text, nullable | |
| created_at | timestamp | |

### `categories`
id, business_id (FK), title, emoji, sort_order

### `services`
id, business_id (FK), category_id (FK), title, description, price, price_label, duration, features (jsonb-массив), before_after_images (jsonb), is_active

### `clients` — конечный клиент бизнеса
id, business_id (FK), telegram_user_id, first_name, username, photo_url, created_at

### `orders`
id, business_id (FK), client_id (FK), service_id (FK), brief_text, urgency, attached_file_id (Telegram file_id, см. раздел 4), status (`accepted`→`in_progress`→`review`→`done`), price_paid, telegram_payment_charge_id, calendar_event_id (nullable), created_at, updated_at

Каждая таблица содержит `business_id` — это и есть вся «мультитенантность»: обычный `WHERE business_id = ...` в каждом запросе. Никакой отдельной подсистемы биллинга/подписки между бизнесами не нужно — если продадите бота клиенту, деньги за это берёте напрямую (как за любой проект), а не через встроенный в приложение платёж.

## 2. Как Mini App понимает, «чей» он сейчас

Один и тот же статический `tg-app/` обслуживает любое количество бизнесов без пересборки:

1. Боту каждого бизнеса в BotFather (`/setmenubutton`) прописывается ссылка вида `https://ваш-домен/?b=<business_id>`.
2. Mini App при старте читает `b` из URL и все запросы к API идут как `/api/business/<business_id>/...`.
3. **Проверка подлинности:** `initData`, которую присылает Telegram, подписана HMAC-SHA256 ключом, сделанным из `bot_token` **конкретного бота**, через который открыт Mini App. Бэкенд обязан валидировать подпись именно тем `bot_token`, что хранится в БД под этим `business_id` — иначе подпись не сойдётся. Это единственное отличие от обычной Telegram-авторизации одного бота.

Для вашего единственного сейчас бизнеса это просто означает: в ссылке будет фиксированный `b=<ваш-business-id>`, и всё.

## 3. Нужные API

### Публичные (клиентский Mini App, требуют `initData`)
- `GET /api/business/:id/catalog` — категории + услуги
- `POST /api/business/:id/orders` — создать заказ (бриф)
- `POST /api/business/:id/orders/:orderId/invoice` — бэкенд вызывает Bot API `createInvoiceLink` (Stars) от имени бота этого бизнеса, возвращает ссылку фронтенду для `openInvoice()`
- `GET /api/business/:id/orders` — заказы текущего клиента (по `initData.user.id`)

### Для вас как владельца/оператора (внутренняя админка, не публичная)
- `GET/PATCH /api/business/:id/orders/:orderId/status` — смена статуса заказа → триггерит `sendMessage` клиенту через бота бизнеса
- `CRUD /api/business/:id/categories`, `CRUD /api/business/:id/services`
- `POST /api/business/:id/google/connect`, `GET /api/business/:id/google/callback` — OAuth2 с Google (опционально)
- `POST /api/businesses` — добавить новый бизнес (когда продадите бота клиенту): принимает bot_token, вызывает `getMe` (проверка) и `setWebhook`, создаёт запись. Вызываете вручную вы, не клиент.

Эта админка может быть даже не отдельным UI на первом этапе, а просто защищённые эндпоинты, которые вы дёргаете сами (Postman/curl) или простая HTML-страница с паролем — полноценную панель имеет смысл строить, когда бизнесов станет больше одного.

### Вебхук
- `POST /webhook/:businessId` — апдейты бота конкретного бизнеса (сообщения, `pre_checkout_query`, `successful_payment`). Один путь на бизнес — Telegram отправляет апдейты именно туда, куда вы указали при `setWebhook`.

Проверяйте заголовок `X-Telegram-Bot-Api-Secret-Token` (вы сами его зададите при `setWebhook`) — иначе кто угодно сможет слать поддельные апдейты на публичный URL.

## 4. Внешние API и хранение файлов

- **Telegram Bot API** (свой токен на бизнес): `setWebhook`, `getMe`, `sendMessage`, `sendDocument` (переслать файл брифа вам, а готовый результат — клиенту), `answerPreCheckoutQuery`, `createInvoiceLink`.
- **Файлы брифа/результата:** отдельное хранилище (S3 и т.п.) не нужно — используйте сам Telegram. Mini App загружает файл на бэкенд → бэкенд пересылает его вам через `sendDocument` → сохраняет полученный `file_id` в заказе. Бесплатно и в пределах существующей инфраструктуры.
- **Google Calendar API** (опционально, можно отложить на этап 2): OAuth2 + `calendar.events.insert`, одностороннее — оплаченный заказ создаёт событие в вашем календаре. Требует завести проект в Google Cloud Console и получить `client_id`/`client_secret` — разовая ручная настройка вне кода.

## 5. Стек и хостинг

- **Backend:** Node.js + Express на Vercel Serverless Functions — тот же аккаунт Vercel, что уже настроен для `tg-app`.
- **База данных:** Postgres на Neon (бесплатный тариф, нативно работает с Vercel).
- **Секреты** (`bot_token`, `google_refresh_token`): шифровать перед записью (AES-256-GCM, ключ — новая переменная `ENCRYPTION_KEY` рядом с уже существующим `BOT_TOKEN` в `.env`).

## 6. Порядок разработки

**Этап 1 — рабочий бэкенд для «Нейро.Студия»:**
Таблицы БД (уже с `business_id` везде, но пока одна запись в `businesses` — ваша), вебхук на ваш бот, каталог из БД вместо `data.js`, создание заказа, оплата через Stars, ручная смена статуса → сообщение клиенту, пересылка файлов брифа через `sendDocument`.

**Этап 2 — Google Calendar (опционально, когда понадобится):**
OAuth-подключение вашего календаря, событие при новом оплаченном заказе.

**Этап 3 — когда появится реальный клиент «купить бота»:**
Заводите вторую запись в `businesses` с его `bot_token`, при необходимости — его категории/услуги. Код фронтенда и бэкенда не меняется вообще — именно ради этого таблицы с самого начала спроектированы с `business_id`.

## 7. Что сознательно остаётся вне плана

- Самостоятельная регистрация клиентов («приведи свой бот и настройся сам») — не строим, пока это не станет реальной необходимостью с потоком клиентов.
- Встроенная подписка/биллинг между вами и будущими клиентами — монетизацию продажи бота ведёте вне приложения (как обычный проект/услугу).
- Автоматическая ИИ-генерация — заказ по-прежнему выполняете вы вручную/полуавтоматически.
- Публичные отзывы/рейтинги, мультиязычность — как и в brief.md, раздел 3.
